# Backend

FastAPI app using `uv`, a `src/` layout, async SQLAlchemy 2.0 + asyncpg
(PostgreSQL), and Alembic migrations.

## Layout

```
backend/
├── pyproject.toml          deps + ruff + pytest config
├── alembic.ini, alembic/   migrations
├── src/app/
│   ├── main.py             create_app() factory
│   ├── core/
│   │   ├── config.py       Settings (pydantic-settings)
│   │   └── database.py     async engine + session dependency
│   ├── api/router.py       aggregates subproject routers under /api
│   ├── health/             no-DB example subproject
│   ├── llm_bench/          feature subproject
│   ├── serving_engines/    feature subproject
│   ├── silicon/            feature subproject
│   └── intel_bluelens/     feature subproject
└── tests/                  pytest suite
```

## A subproject

Each feature is a self-contained package directly under `src/app/<name>/`,
colocating its routes and business logic. It has up to four files:

| File         | Responsibility                                  |
| ------------ | ----------------------------------------------- |
| `router.py`  | `APIRouter` + path operations (transport)       |
| `schemas.py` | Pydantic request/response models (contract)     |
| `service.py` | Business logic / DB access                       |
| `models.py`  | SQLAlchemy ORM models (only if it needs the DB) |

Register it by adding one line to the `DOMAINS` list in `api/router.py`:

```python
("app.<name>", "/<name>", "<name>"),
```

> Prefer the `add-domain` skill to scaffold a new subproject consistently.

## Configuration

`core/config.py` is the single source of truth for runtime config. It loads
environment variables (and an optional `.env` file) via pydantic-settings — add
new settings there rather than reading `os.environ` elsewhere. Database keys:

| Setting        | Env var        | Default                                                        | Purpose                          |
| -------------- | -------------- | ------------------------------------------------------------- | -------------------------------- |
| `database_url` | `DATABASE_URL` | `postgresql+asyncpg://postgres:postgres@localhost:5432/intel_ai` | Async SQLAlchemy connection URL  |
| `db_echo`      | `DB_ECHO`      | `false`                                                       | Log emitted SQL (debugging)      |

> The URL **must** use the async driver prefix `postgresql+asyncpg://`. Copy
> `backend/.env.example` to `backend/.env` and adjust credentials for local dev.

`core/database.py` builds the async `engine`, the `SessionLocal` factory, the
`get_db()` request dependency, and the shared declarative `Base`. ORM models in
each subproject's `models.py` inherit from `Base`, and `import_domain_models()`
(in `api/router.py`) imports them so they register on `Base.metadata`.

## Database & migrations (Alembic)

Migrations live in `alembic/versions/`. The environment (`alembic/env.py`)
pulls the connection URL from `settings.database_url` and calls
`import_domain_models()` so autogenerate sees every subproject's tables against
the shared `Base.metadata` — no hard-coded URL or model list to maintain.

**Workflow when you add or change a model:**

```bash
# 1. Make sure the DB is running and reachable (docker compose up -d db, etc.)
# 2. Autogenerate a revision from the diff between models and the DB
make migration m="add users table"     # → alembic revision --autogenerate -m ...
# 3. REVIEW the generated file in alembic/versions/ before committing
#    (autogenerate can miss renames, server defaults, enum/index changes)
# 4. Apply it
make migrate                            # → alembic upgrade head
```

**Common commands** (run inside `backend/`, prefixed with `uv run`):

```bash
uv run alembic upgrade head             # apply all pending migrations
uv run alembic downgrade -1             # roll back the last migration
uv run alembic downgrade base           # roll back everything
uv run alembic current                  # show the DB's current revision
uv run alembic history --verbose        # list the full revision chain
uv run alembic revision -m "manual"     # empty revision (hand-written DDL/data)
uv run alembic stamp head               # mark DB as up-to-date without running
```

Notes:

- **Always review autogenerated revisions** — Alembic compares metadata to the
  live DB and can produce incomplete `upgrade()`/`downgrade()` for column
  renames, type changes, or data migrations. Edit them by hand as needed.
- A new subproject's tables are only detected once its `models.py` is imported,
  which happens automatically via `import_domain_models()`.
- For first-time setup with no migrations yet, generate the initial revision
  with `make migration m="initial"`, review it, then `make migrate`.
- `init_db()` in `core/database.py` does `create_all` for **dev/test only**;
  production schema changes must go through Alembic migrations.

## Testing

`tests/conftest.py` provides an async httpx client against the app with an
isolated test database. Run with `make test` (or `uv run pytest`).
